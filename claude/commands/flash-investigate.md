บรีฟ: $ARGUMENTS · ว่าง → ถาม user (AskUserQuestion) ว่าให้สืบเรื่องอะไร

## 1. เขียนบรีฟให้ครบ 4 ช่อง (ผู้สืบเห็นแค่บรีฟ ไม่เห็นบทสนทนา · บรีฟคือหัวใจ — ผิดจุดตั้งแต่ต้นผลก็ผิดทั้งชุด)
1. **อาการ** — สิ่งที่เห็นจริงตรงตัว: ข้อความ error / ค่าที่ได้ vs ที่ควรได้ / ขั้นตอนทำซ้ำ (copy มาเอง ห้ามสรุปตามความเข้าใจ)
2. **จุดที่น่าจะเกี่ยว** — โมดูล/ไฟล์/ฟังก์ชันที่รู้แล้ว (ไม่รู้ = เขียนว่าไม่รู้ ห้ามเดาใส่)
3. **ที่ตัดทิ้งแล้ว** — สิ่งที่ลองแล้ว/พิสูจน์แล้วว่าไม่ใช่ (กันวนซ้ำ) และบั๊กเก่าที่คล้ายกัน
4. **สิ่งที่ต้องคืน** — ต้นตอ 1 ประโยค + `ไฟล์:บรรทัด` พร้อมโค้ดที่คัดตรงตัว + วิธีพิสูจน์ + ระดับมั่นใจ · **ห้ามแก้ไฟล์**

ก่อนส่ง ตรวจเอง: (ก) ข้อ 1 มีของจริงที่ copy มา ไม่ใช่คำอธิบายกว้าง ๆ (ข) ไม่มีข้อสันนิษฐานของคุณปนเป็นข้อเท็จจริง — ถ้ามีให้ติดป้าย "(สมมติฐาน)" (ค) ผู้สืบทำตามบรีฟนี้ได้โดยไม่ต้องถามกลับ
ถ้าบรีฟไม่พอ ผู้สืบจะตอบ `บรีฟไม่พอ: ขาด …` → เติมแล้วส่งใหม่ (ห้ามถือเป็นผลสืบ)

## 2. ส่งงาน (อ่านอย่างเดียว ไม่ชนงานอื่นในคิว)
```
python {{FLASHQ}}/flashq.py investigate "<บรีฟ 4 ช่อง>" --project "<path โปรเจกต์>" --auto
```
- ใช้ `--project` ถ้าไม่ได้อยู่ในโปรเจกต์นั้น · บรีฟหลายบรรทัดใส่ในเครื่องหมายคำพูดได้ · รันใน background (`run_in_background: true` คำสั่งเดียวตรง ๆ — ห้าม `&` · sleep · head/tail · ยาม `run_guard.py` บล็อก)
- ต้องมี agent `flash-investigator` (มาจาก `flashq.py install`) ไม่มี/เป็น subagent → flashq จะรายงาน `FAIL` พร้อมคำแนะนำ
- โควตาหมด → flashq ย้าย provider เป็นโมเดลเดิมให้เอง (ค่าเริ่มต้น 2 ครั้ง)
- **บั๊กกำกวม / เคยแก้แล้วไม่หาย → สืบ 2 session** (อีกตัวใส่ `--model` คนละโมเดล/คนละตระกูล) แล้วเทียบ `file:line` ต้องตรงกัน

## 3. อ่านผล
- `FLASH_RUN=OK` → อ่านรายงานจากท้ายผลลัพธ์ (หรือ `python {{FLASHQ}}/flashq.py log <job>`)
- `FAIL` / `TIMEOUT` / `QUOTA` → บอก user ตามจริง ห้ามเดาผลเอง · **ห้ามไล่โค้ดสืบเองแทน** → ถาม user (AskUserQuestion): "แบ่งบรีฟให้แคบลงแล้วส่งใหม่ (แนะนำ)" / "สืบใหม่ด้วยโมเดลอื่น (`--model`)" / "ให้ Claude สืบเอง (กินโควตา Claude)" / "หยุดก่อน"
- บรรทัด `CITATIONS: ตรงถึงโค้ด N · ตรงแค่ไฟล์/บรรทัด K · ผิด M` (flashq ตรวจกลไกว่า `ไฟล์:บรรทัด` ที่อ้างมีจริง · "ตรงถึงโค้ด" = โค้ดที่คัดไว้อยู่ในบรรทัดนั้นจริง · "ตรงแค่ไฟล์/บรรทัด" = ผู้สืบไม่ได้คัดโค้ดมา ต้องเปิดดูเอง) → ข้อที่ ✗ = **ห้ามเชื่อข้อนั้น** · ผ่านครบแปลว่า "อ้างตรงโค้ดจริง" เท่านั้น ยังไม่ได้แปลว่าเป็นต้นตอ

## 4. ตรวจก่อนเชื่อ (สำคัญ)
- **เปิดโค้ดจริงที่ `ไฟล์:บรรทัด` ของข้อสรุปหลัก 1–2 จุด** แล้วเทียบว่าอธิบายอาการได้จริง (flow จากอาการมาถึงจุดนั้น) · ไม่ใช่แค่อ้างตรง
- สองผู้สืบชี้ต่างกัน / มั่นใจระดับกลางหรือต่ำ → ยังไม่ใช่ต้นตอที่ยืนยัน ห้ามเขียนแผนแก้ให้ Flash จากข้อสรุปนี้
- ต้นตอที่ยืนยันแล้วค่อยสรุปให้ user / เขียนแผนแก้ (`/flash-plan`) · ที่ยังไม่แน่ใจให้บอกว่า "ยังไม่ยืนยัน"
