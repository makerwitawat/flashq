ชุดที่ต้องการ: $ARGUMENTS · ว่าง → ทุกชุดที่ตั้งไว้ในโปรเจกต์ (`.flash.json` → `qa.presets`)

## 1. หลักการ (ทำไมเชื่อผลนี้ได้)
- **flashq รันคำสั่งทดสอบเอง** แล้วตัดสินจาก **exit code จริง** (+ ข้อความ `expect` ที่ต้องพบ ถ้าตั้งไว้) — ไม่มี AI มาบอกว่า "ผ่านแล้ว" · Flash เข้ามาเฉพาะตอน **ล้ม** เพื่ออ่าน log อธิบายสาเหตุ และคำอธิบายนั้น **เป็นความเห็น ไม่เปลี่ยนคำตัดสิน**
- fail-closed: exit 0 แต่ไม่พบข้อความที่ต้องมี (`NOEXPECT` เช่น "collected 0 items") = **ไม่ผ่าน** · ล้มรอบแรกแต่ผ่านรอบรันซ้ำ (`FLAKY`) = **ไม่ผ่าน** · `HEAD` เปลี่ยนระหว่างทดสอบ = **ผลใช้ไม่ได้**
- นักทดสอบ **ไม่รันคู่กับงานที่แก้ไฟล์ในโปรเจกต์เดียวกัน** (ตัวจัดคิวกันให้) → ทดสอบโค้ดที่นิ่งเสมอ · ทดสอบ **โค้ดที่อยู่ใน checkout หลักตอนนี้** (ไม่สลับ commit ให้) → จะทดสอบผลของงาน Flash ให้ merge/commit เข้า checkout หลักก่อน แล้วใส่ `--commit <sha>` เพื่อยืนยันว่าทดสอบ commit นั้นจริง

## 2. เตรียมชุดทดสอบ (ครั้งแรกของโปรเจกต์)
ใน `.flash.json` ของโปรเจกต์ (ผู้ใช้ยืนยันก่อนเพิ่ม — ห้ามใส่คำสั่งที่เดาเองโดยไม่บอก):
```json
{"qa": {"presets": {
  "unit": {"cmd": "python -m pytest -q", "expect": "\\d+ passed", "timeout_min": 20},
  "lint": "ruff check ."
}}}
```
- `cmd` = คำสั่งบรรทัดเดียว (รันที่รากโปรเจกต์ หรือ `cwd` ใต้โปรเจกต์) · `expect` = regex ที่ต้องพบใน output ถึงนับว่าผ่าน (กัน "รันแล้วไม่มีเทสต์สักข้อ") · `timeout_min` (ค่าเริ่มต้น 30) · `idle_min` (log เงียบเกินนี้ = ค้าง · ค่าเริ่มต้นปิด) · `retry` (0-3 · ค่าเริ่มต้น 1: ล้มแล้วลองซ้ำ 1 รอบ ผ่านเฉพาะรอบหลัง = `FLAKY` ยังไม่ผ่าน) · `cmds` (หลายคำสั่งในชุดเดียว แยกผลทีละคำสั่ง เช่น `"cmds": ["python tests/test_a.py", "python tests/test_b.py"]` — ใช้กับสคริปต์ทดสอบที่ไม่พึ่ง pytest) · `env_exit` (เลข exit code ที่หมายถึง "สภาพแวดล้อมไม่พร้อม" เช่น server ไม่ขึ้น → ผล `ENV` ไม่ลองซ้ำ ไม่ให้ Flash เดา)
- ยังไม่มีชุด → `python {{FLASHQ}}/flashq.py qa --project "<path>"` จะบอกสิ่งที่เดาได้จากไฟล์ในโปรเจกต์ (ไม่รันเอง) → เสนอผู้ใช้แล้วค่อยเขียนลง `.flash.json`

## 3. สั่งทดสอบ
```
python {{FLASHQ}}/flashq.py qa [ชุด...] [--commit <sha>] [--project "<path>"]
```
- รันใน background (นานเท่าชุดทดสอบ) · ไม่ระบุชุด = ทุกชุด · ครั้งเดียวไม่ต้องตั้งชุด: `--cmd "<คำสั่ง>"` (ใช้ได้เฉพาะจาก CLI)
- ไม่อยากให้ Flash อธิบายตอนล้ม: `--no-analyze` (ไม่เรียกโมเดลเลย) · ล้มแล้วหยุด: `--fail-fast` · รันซ้ำแยกไม่นิ่ง: `--retry 1`
- รอผล: `python {{FLASHQ}}/flashq.py wait <job>` (ไม่ต้อง sleep/poll)

### ทดสอบหน้าเว็บแบบเงียบ (Chrome headless · Playwright)
- เขียนสคริปต์ `tests/ui_*.py` (ใช้ `playwright.sync_api` + `chromium.launch(headless=True)`) แล้วตั้งเป็นชุด `ui`: `{"cmds": ["python tests/ui_smoke.py"], "env_exit": 3}` — `flashq qa` เดาให้เองเมื่อเจอไฟล์ที่ import playwright
- headless สั่งผ่าน CDP: **ไม่มีหน้าต่าง ไม่ขยับเมาส์/คีย์บอร์ดจริง** ห้ามใช้ headed หรือ computer-use ในชุดทดสอบ · สคริปต์ต้องรัน server ของตัวเองบนพอร์ตแยก + ข้อมูลชั่วคราว ไม่แตะของจริง
- ต้องมี `pip install playwright` + `playwright install chromium-headless-shell` · ไม่มี = สคริปต์ออก exit 3 → ผล `ENV` (ยังไม่ได้ทดสอบ ไม่ใช่โค้ดผิด)
- หลายเรื่องในครั้งเดียว: ตั้งหลายชุด (`unit` `ui` `lint`) แล้วสั่ง `qa unit ui` หรือใส่หลายไฟล์ใน `cmds` ของชุดเดียว (แยกผลทีละไฟล์)
- อยากให้โมเดลสำรวจหน้าเว็บเอง (ไม่ใช่ชุดตายตัว) → ใช้ Playwright MCP แบบ `--headless --isolated` ใน opencode แยกต่างหาก · คำตัดสินของนักทดสอบยังมาจาก exit code เท่านั้น

## 4. รายงานผู้ใช้ (ภาษาไทย ครบทุกข้อ)
1. **ทดสอบอะไร** — โปรเจกต์ · ชุดไหน · commit ไหน (+ ไฟล์ที่แก้แต่ยังไม่ commit / ไฟล์ใหม่ที่ไม่ติดตาม ตามที่หัวสรุปบอก · แยกให้ผู้ใช้เห็นว่าไฟล์ใหม่ส่วนใหญ่อาจไม่เกี่ยวกับโค้ดที่ทดสอบ)
2. **ผล** ✅/❌/⏱/⚠️ ต่อชุด จากบรรทัดสรุป `QA=` (ห้ามเปลี่ยนคำตัดสินเอง)
3. **ถ้าไม่ผ่าน**: สาเหตุเป็นภาษาคน จาก **log จริง** (`python {{FLASHQ}}/flashq.py log <job>` มี path log + บรรทัดสำคัญ) — คำอธิบายของ Flash ต้องเทียบกับ log ก่อนเชื่อ · แยกให้ได้ว่า โค้ดผิด / เทสต์ผิด / สภาพแวดล้อม / ไม่นิ่ง
4. **ผู้ใช้ต้องทำอะไรต่อ** — เช่น สั่ง Flash แก้ (ผ่าน `/flash-plan`) · แก้เทสต์ · ตรวจสภาพแวดล้อม · ไม่ต้องทำอะไร
- `ENV` = ยังไม่ได้ทดสอบโค้ดจริงเพราะสภาพแวดล้อมไม่พร้อม (เช่น server/DB ไม่ขึ้น) → บอกผู้ใช้ว่าต้องเตรียมอะไร ห้ามสรุปว่าโค้ดผิดหรือผ่าน
- `NOEXPECT` / `FLAKY` / "HEAD เปลี่ยน" / `TIMEOUT` ต้องอธิบายตรง ๆ ว่าหมายถึงอะไร — **ห้ามรายงานว่า "ผ่าน" เมื่อ `QA=` ไม่ใช่ PASS**
